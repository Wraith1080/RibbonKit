## Native page ownership and application integration

Create a UserControl class in the consuming app and use its normal VS designer
to author labels, editors, bindings and layout. The recommended designer workflow
now selects its class through ContentType, as described below. For existing
application-owned instances, instantiate without parenting, then assign to the
page after `InitializeComponent`:

```csharp
infoContent = new DocumentInfoControl();
infoPage.Content = infoContent;
```

Keep that reference in the app. In the host's existing disposal path, release the
page's Content (or dispose its declaration/ribbon), then dispose the app-owned
UserControl. Do not add a second Dispose override alongside one generated by VS.
A control already placed on the Form cannot be borrowed as page content; do not
detach a designer-owned Form child to work around this restriction. One native
Control is assigned to one page. Editing/removing a page releases it without
disposing the application control. Application-created content may be absent in
the design server's metadata because application constructor code is not the
generated initializer; that does not mean the runtime assignment is missing.

The independent fixture includes **BackstageInfoControl.cs** and its designer
(TableLayoutPanel plus a FlowLayoutPanel of actions), and **BackstagePrintControl.cs**
with a native orientation choice. Its generated Form initializer selects both
classes through ContentType; no application constructor assignment or special
page base class is needed. The runtime Notes field and Save command demonstrate
public Content/event integration without Showcase.

## Transactions and compatibility

Read/commit/preview use a separate design endpoint and snapshot; the existing
ribbon editor retains its workflow. Shared icon/scalar read helpers and the
client property descriptors are reused. Settings/properties are checked against
server-owned schemas, converted and validated on detached built-in declarations
before mutation. Duplicate/reserved names and IDs, stale drafts/content references,
unsupported types/children, invalid SVG/width/opacity and removal of a QAT source
are rejected before live changes. The client cannot assign live native Content;
it can select a server-discovered UserControl class for ContentType.

Existing pages/commands keep their component identity, Content, borrowed images,
custom providers, bindings and events. Unchanged SVG providers remain the same
instances. New models are created/sited by the designer host; removed models are
destroyed through it. Selection/preview sizing is excluded from the revision and
does not create an authoring transaction. Actual VS Undo/Redo/generated-code
behavior remains a separate user gate.

## UserControl page assignment — 2026-11-01

are exclusive; attempting to select a class while borrowed content is assigned

serialization excludes a realized owned instance and saves `typeof(...)` instead;

types. It inspects metadata without instantiating application controls. Build the

## Runtime instantiation timing correction — 2026-11-01

The user reported that ContentType pages were instantiated only when clicked and
requested creation at form load. They also explicitly requested documenting the
instantiation timing. The current contract is:

- Runtime `RibbonControl.EndInit` creates **all** declared ContentType instances,
  including hidden/disabled pages. Normal designer-generated InitializeComponent
  finishes this batch before Form.Load, so the application can configure every
  page through its Content reference without first opening Backstage.
- Runtime OnCreateControl supplies the same initialization for code-built
  consumers that omit an init batch. Hand-built/initially hidden ribbons should
  use matching BeginInit/EndInit to establish an explicit initialization boundary.
- Once initialized, added pages and replacement types are created after their
  model change; an active BeginUpdate/EndUpdate batch defers creation until its end.
- Creation alone does not parent pages into a Backstage surface, open Backstage,
  or force their HWNDs/hidden UserControl.Load events. Those keep normal WinForms
  handle/visibility semantics. Native values, selection and ownership remain
  retained during switching and close/reopen. Designers and previews create no
  application page instances.
- The existing ownership contract remains: ContentType instances are page-owned;
  explicit Content is borrowed. Application constructor failures surface during
  initialization, rather than waiting for a File/page click. No additional public
  property or ownership mode is introduced; the inherited OnCreateControl override
  is recorded in the native API baseline.
