# RibbonKit 1.1 acceptance and release plan

> Planning baseline: 2026-10-22, clean `main` at
> `899e53ffea18bc5f1a377dc09d9700edb85781a4` (Writer integration merged in PR #31).
> A1 source review completed 2026-10-22; A2 build/tests have not started. Target:
> `1.1.0`, subject to compiled and runtime confirmation. Project/package version
> remains `1.0.0` until release preparation. This plan does not authorize committing,
> pushing or publishing.

## Scope and ownership

Validate the existing post-v1 library and both consumers as a bounded 1.1 release:
Compact/Touch density, Simplified layout/customization, feature availability,
Crystal and Office 2024 Flat, shared glass/backdrop integration, QAT command
projections/icon choices, gallery/combo/menu improvements, layout transitions,
designer authoring and the completed Writer host integration.

The source revision above is the starting inventory, not a permanently frozen
release candidate. Record the actual source revision and local changes for each
execution. New fixes require an impact-based verification decision; new features
require a scope decision rather than being added to acceptance work implicitly.

User clarification from the **Prepare Writer host for 1.1** chat is carried into
this campaign: physical/native touch and OS IME testing are not required. Exercise
Touch density through mouse, keyboard and automated controls. Existing synthetic
composition/fallback regressions remain useful; they do not imply an IME claim.

Keep these outside 1.1 completion requirements: grouped Writer font UI, automatic
device detection, new document features, editable multipage layout, remaining MDI
milestones, full Windows contrast-theme support, production RTL certification and
physical-printer certification. Retain existing regression coverage and document
known limitations; exclusion does not excuse a regression in supported behavior.

This file owns campaign status, gate decisions and release readiness. Existing
subsystem plans retain their detailed acceptance and implementation evidence.
Record an observation at its owning subsystem and link it here; do not duplicate
confirmation prose across the design index, history and README.

### Intentional behavior and customization notes for A9

- **Office 2007 default File presentation:** the shared style now follows
  `RibbonKit.ApplicationButtonShape.Default`, selecting Orb for Office2007 and
  Tab elsewhere. A consumer relying on the former Office2007 File-tab default can
  retain it with explicit `ApplicationButtonShape="Tab"`. Local values retain WPF
  precedence. This previously approved behavior must be mentioned in 1.1 notes;
  unchanged enum/API/registration metadata does not mean unchanged effective style.
- **Keyboard entry:** Ribbon now overrides Focusable/IsTabStop to false so the
  container is skipped while its commands remain keyboard destinations. This is
  the documented navigation correction, not a removed command or KeyTip API.
  Consumers explicitly focusing the container should review their focus routing.
- **More specific theme tokens:** ScreenTip background now uses
  `RibbonKit.Brushes.ScreenTip.Surface`; RibbonTextBox uses
  `RibbonKit.Brushes.Input.SurfaceBackground` / `.Input.Border`; Options action
  buttons use `.Dialog.ActionBackground` / `.Dialog.ActionBorder`. Legacy keys
  remain, but overrides of the previously shared brushes may no longer repaint
  these individual surfaces. Include an override-mapping note rather than claiming
  complete visual equivalence for custom themes. Menu minimum width now follows
  `RibbonKit.Metrics.MenuItemMinWidth` (200 in the Office dictionaries reviewed,
  versus the old 160-DIP style literal); narrow-window checks remain in A5.
- **Customization template refactoring:** apparent removed TreeViewItem selection/
  expansion setters are inherited from `RibbonKit.Customize.TreeContainerStyle`;
  message actions use a named shared style and gallery side buttons fill their
  allocated rows. These are shared presentation changes, not confirmed missing
  bindings. Preserve the associated runtime/visual checks rather than treating the
  same-file setter comparison as a product failure.
- **New optional presentations:** Compact/Classic remain the runtime defaults.
  Hosts own density/layout selection and persistence; the new Writer preferences
  do not alter document data or rewrite saved ribbon structures. Downgrading a
  profile that selects a new enum value into an old app is not forward-compatibility
  coverage and is not promised by this review.

Static evidence is under `TestResults/v1.1-compatibility/`: `api-enum-inventory.json`,

## Execution order and stop conditions

1. **A1 inventory and compatibility.** Record the execution baseline and confirm
   no unrelated work will be overwritten. Reconcile inherited evidence and known
   gaps. Confirm runtime target frameworks from project files; current runtime is
   net8/net9 and design tooling remains net472.
2. **A2/A3 automated candidate gate.** Follow [CONTRIBUTING](../CONTRIBUTING.md#proportional-validation)
   and the CI sequence: restore, normal Release solution build, then unfiltered
   solution tests. Clear `RIBBONKIT_VISUAL_SCENES`, `RIBBONKIT_PORTABILITY_SCOPE`,
   `RIBBONKIT_CAPTURE_SNAPSHOTS` and `RIBBONKIT_UPDATE_SNAPSHOTS`; preserve/restore
   the caller's environment. Inspect snapshot actual/diff diagnostics before any
   approval/tolerance change. A first failure does not establish later scenes passed.
3. **A4-A6 human review.** Use normal Debug outputs for local review. Keep physical
   mouse/keyboard work in an undisturbed process; capture scope/environment and
   distinguish real interaction from offscreen renders/programmatic screen capture.
   Record unavailable display/motion gates without substituting synthetic proof.
4. **A7/A8 package, designer and stability.** Use normal Release outputs for pack
   and performance. Run `eng/Validate-Package.ps1` for the selected current
   `.nupkg`/`.snupkg` pair; it builds clean net8/net9 consumers. Its `-RunConsumer`
   option additionally launches the net8 smoke; record any net9 launch separately.
   Preserve older packages and avoid ambiguous directories with multiple pairs.
   Check per-TFM DesignTools placement, XML docs, symbols/Source Link and manifest.
   Use [the existing performance script](../eng/Measure-ShowcasePerformance.ps1)
   outside the debugger; record conditions and results without inventing a threshold.
5. **A9 release preparation, later.** After findings are dispositioned, prepare
   version/package metadata and 1.1 notes, preserve the published 1.0.0 record,
   review intentional API additions before recording them as shipped, and build/
   validate the actual final versioned artifacts. Verify checksums and provenance.
   Do not reuse a package generated before source/version changes as final evidence.

For package-reference Visual Studio review, retain accepted project-reference Tab,
Group/Combo defaults, undo/redo and File preview evidence. Close the specific gaps:
package Toolbox discovery, changed-family authoring/preserved assignments, property
editing, save/reload and outstanding transaction scopes. Use a disposable consumer;
do not alter the user's Showcase review XAML or close their apps without need.

Fix failures in bounded slices, select relevant tests/consumers/visual scenes and
retain unaffected passes. Report an initial full run followed by focused repairs as
assembled coverage, not a clean single final-source full-suite pass. Broaden/rerun
only for changed impact, a failed gate or unresolved risk, and record why.

Crashes, data loss, settings/customization corruption, broken commands or accidental
public API breaks block stable release. Other visual, platform, designer or
accessibility findings require a recorded resolution: corrected with evidence,
removed from the release promise, or explicitly accepted as a documented limitation.
Do not silently convert a failed or unavailable gate into Passed.

## Final release decision

Before declaring 1.1 ready, every A/W row must have evidence or an explicit
disposition. Identify the final source/artifacts, outstanding limitations and what
was not tested. The user makes the stable-release decision from that record.
Hardware-dependent gates may be deferred only through a visible disposition.

GitHub Releases remains the distribution route; NuGet.org publication is not
planned. Committing, pushing, tagging, creating a GitHub release and uploading
assets remain separate actions requiring user instruction. None is performed by
creating this plan, and no scheduled follow-up is created.
